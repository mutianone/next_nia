# 笔录后台生成与验收

当前实现保留 React/FastAPI，不增加 Dify 运行依赖。语音转写保存后，前端提交后台生成任务；页面可以离开或刷新，返回后读取数据库中的任务进度。每组最多 10 个字段，按顺序处理，最多同时处理两份笔录，全局最多排队 8 份。这个队列目前面向单进程部署，不应使用多个 Uvicorn worker。

## 失败和人工修改

- 各组结果通过现有字段及片段引用校验后才保存检查点。全部完成后一次性写入成文，失败不会用半份结果替换正文。
- “继续未完成分组”只重发失败及尚未完成的组，已完成组不重发。重启不自动外发资料，需用户主动继续。
- 文字、模板、人工修改或模型变化后不能接续旧任务。版本冲突时不覆盖当前资料。
- 人工修改的模板字段保存后自动保护，包括人工清空的字段。重新生成保留保护值，也不伪造其 AI 来源。点击“允许 AI 重填”解除保护。
- 删除原音会清除对应转写、关联修订及合并生成结果，也清除后台任务的输入和分组输出。正在处理时禁止删除。
- 当前保留旧同步 `/analyze` 接口供兼容使用，新页面使用 `/generation-jobs`。语音转写仍是独立请求。

## Dify 对照方法

实际部署或提供 Dify 服务后才能报告对比结果，脚本本身不是实测结论。Dify 与当前实现必须使用相同模型、相同参数、相同分组和相同校验，不应把换模型带来的差异归因于工作流平台。

在独立 Dify 测试环境中建立 Workflow：开始 → LLM → 结束。

1. 开始节点添加两个段落字符串变量：`system_prompt` 和 `payload`。
2. LLM 选择与当前项目相同服务商和模型；System 引用 `system_prompt`，User 引用 `payload`。启用 JSON 对象输出，关闭思考模式（与本项目模型适配一致），输出上限 6000 tokens。不要另外添加知识库、提示词或检索节点，以免比较口径不同。
3. 结束节点输出 `result`，映射 LLM 的文本结果。发布后创建仅用于测试的应用 API Key，保存在终端环境变量中。
4. 同样运行三种样本各三次，比较完成率、总耗时、分组耗时、字段事实检查，以及人工阅读完整结果后的错误类型。维护成本另外记录部署服务数、升级步骤和故障排查时间，不能从一次调用耗时推断。

```sh
# 只会发送固定虚构样本，不读取业务笔录；仍会消耗配置模型的 API 额度。
backend/.venv/bin/python scripts/benchmark-record-generation.py --engine native --runs 3 --confirmed-cloud --output output/record-benchmark/native.json

# 先在当前终端配置 DIFY_API_BASE 和 DIFY_API_KEY，再运行；不要将密钥写入代码或报告。
backend/.venv/bin/python scripts/benchmark-record-generation.py --engine dify --runs 3 --confirmed-cloud --output output/record-benchmark/dify.json
```

参考：[Dify Workflow API](https://docs.dify.ai/en/api-reference/guides/workflow)。Dify API Key 仅在后端使用；运行脚本不会把 Dify 接入正式业务页面。


## 逐字依据校验（2026-11-09）
问答字段现在使用 question/answer 原文引用，服务器验证定位、相邻关系、题目词语匹配、完整句边界及 value 与原文一致性。未通过字段留空并显示原因。规则是保守筛查，不等于识别了说话人或证明语义正确；同音字保留待核对。人工保护值继续保留。

审核面板直接对照候选与生成时原文快照；没有音频时间戳时只能从片段起点回听。问题、回答的文字位置不冒充音频时间位置。

后台针对429/503/504最多重试两次，429等待65/130秒，临时不可用等待3/6秒；身份、格式和引用失败不重试。重试前复核版本。来源、模板、人工保护字段、模型与校验版本不变且无拦截项时复用结果；旧校验任务必须重新生成。

固定规则集：`backend/tests/fixtures/record_acceptance/quality_cases.json`。运行：
```sh
backend/.venv/bin/python scripts/check-record-quality.py --output artifacts/record-quality/rules.json
backend/.venv/bin/python scripts/check-record-quality.py --cloud --runs 1 --output artifacts/record-quality/cloud.json
```
第二条使用已配置云端服务发送现有全虚构金子测试音频的转写，仅测试三个曾出错的字段，不写业务数据库。可用`--model`仅在本次进程比较同一服务商其他模型，`--runs 3`记录重复结果与耗时；不改变全局配置。报告保留字段、拦截项、耗时及服务商返回的token用量。费用以服务商账单为准。

规则测试覆盖三种真实模板、否认、限定、不确定、提问混入、错配、缺引用、长文本及多段来源。它不覆盖真实口音、噪声、双音色识别率与人工修改时间；这些需要音频验收与人工基准，不能把规则通过率称为整体准确率。


## 2026-11-09 原文编号回填

当前 extractive-qa-v2 先由后端形成明确问号边界的问答候选，模型仅选择问答编号与模板字段，后端依据原文位置提取答案，保留既有人工保护和质量检查。无法可靠分句时不保证回填；不自动修正原始转写错字。坏编号按字段隔离，重复文本按位置回溯。

134项后端专项、4项前端专项通过。真实原始虚构录音的转写两次云端测试分别0/3、1/3通过，约3秒；独立构造的清晰问答对照两次3/3通过，约3秒。不能将对照样本结果视为真实音频准确率。详见 artifacts/record-quality/编号回填优化结果.txt。


## 2026-11-09 独立问答整理

人工修订页新增整理问答，POST /api/records/{id}/qa-proposal 只返回候选，不落地修改片段。用户逐段确认角色后通过原有segments接口保存并留存版本。云端建议不可自动成为确认角色；所有来源必须全文精确覆盖，失败保留原文供人工拆分。单次限制10000字，无逐句时间戳时只回听原音或已有来源片段起点。

当前SenseVoiceSmall真实探测无说话人和时间戳字段，详见 artifacts/record-quality/asr-capability.json。原文整理实测与边界记录于 artifacts/record-quality/问答整理验证说明.txt。


### 说话人边界贯穿回填（extractive-qa-v3）

保留输入角色，已确认角色优先于问号分句；下一位询问人发言终止答案。未知声学编号不得推断为业务角色。云端结构化转写保留中性说话人标签与片段时间，上传音频保存独立片段；连续录音保留分段标签，但暂不恢复句级时间，不能跨音频批次合并相同编号的声音。整理问答对完整声学标签材料直接使用原有边界，避免再次调用文本模型猜测；同音频同声音可一次确认角色。

111项后端回归和8项前端测试通过，生产构建通过。使用此前283秒虚构录音的48段云端原始转写，按已知脚本人工映射声音1/2角色，不改字，调用现有云端回填模型两次：三个重点问题均2项通过（3.21秒、2.96秒），q021因问题匹配不足拦截。这里只验证三个重点问题，非完整模板验收；原始转写存在句尾缺字，不能把通过校验当作完整准确。

默认模型未切换；SenseVoice原文仍可能粘连。当前完成结构化分段和已确认角色链路，未完成自动声学身份确认或缺字恢复。历史记录未自动改写。旧v2结果提示重新生成。


### 缺尾修复和语义复核（extractive-qa-v4）

音频缺尾与问答匹配改进验证（2026-11-11）

1. 原始WAV与本地归一化MP3时长分别为283.007574秒、283.007625秒；同一完整录音两种格式均在话者分离接口出现相似缺尾。本地转码没有显示整段尾部截断，不能据此断言所有录音均无采集问题。
2. 新增原音补转写：按已定位片段向前200ms、向后最多1500ms补足上下文，不跨下一位已知发言开始点；重叠发言拒绝自动截取。使用SenseVoiceSmall二次识别，只显示候选，用户选择采用才进入修订，原始转写不改写。短音频标准WAV头修复后，三处实际云端结果：
   嗯 -> 嗯，听明白了。（0.50秒）
   我没有重大疾病，不申请回。 -> 我没有重大疾病，不申请回避。（0.49秒）
   入境日期我还不确。 -> 入境日期我还不确定。（0.64秒）
3. 连续录音45秒以后优先寻找分片边界停顿；60秒仍在说话时继续等待，最多90秒。保存PCM连续性和停止尾段确认保持，硬上限处仍可能切句，不宣称完全消除所有边界问题。没有可靠时间戳的片段不能直接使用补转写按钮。
4. 对仅因文字重合不足被拦截的匹配，增加一次最长30秒的独立云端语义复核。无效/失败响应维持原拦截；角色、原文引用、否认、改写校验不放宽。语义通过的字段仍标记待核对。
5. 使用上一轮已保存的48个云端发言片段，人工根据虚构脚本确认角色，不改原文，三道重点问题两次均3/3通过，耗时4.03秒、8.52秒。旧方案同样材料为2/3。保留“我认为是真的，但请核查”等限定，不生成证件真实的法律结论。语义复核只能核验相关性，不能证明转写准确；这不是整张模板或真实噪声录音的100%准确率。

没有自动切换默认模型或改写业务数据库。当前SenseVoice转写仍可能粘连；新流程需要声学分段或人工确认的角色边界。补转写不是全自动后台修字，用户可在问答整理界面比较并采用候选。

验证：119项相关后端测试、13项前端测试；生产构建。最终以本轮实际测试日志为准。
